Act VII

Boundaries

By Tuesday, the interesting part is not how much more the system can do. It is how much more precisely it can decide what it is allowed to do, what evidence counts, and when it should stop.

Tuesday · ownership and recovery

Autonomy got stricter

One of the harder problems turns out to be retry behavior. If two workers can see the same task, or one worker disappears halfway through, “just try again” sounds harmless until the thing being retried can actually change state somewhere else.

So the execution model gets narrower. Claims become scoped to the project, branch and task. Recovery is allowed only for work that is still clearly pre-submission and has actually expired. Once submission may have happened, elapsed time is no longer permission to repeat it.

This is a different version of autonomy than I pictured a few days ago. The system is not becoming more autonomous because it retries more. It is becoming more autonomous because it can tell the difference between safe recovery and dangerous duplication.
What changedBefore: ownership and retries were mostly an execution-detail problem.
Now: ownership, generation/fencing, submission phase and evidence are part of the product contract.

Rule: abandoned pre-submission work can be recovered under explicit fences. Ambiguous or submitted work does not become retryable just because time passed.

October 24 · an experiment that didn't earn its way in

Learning when to undo the improvement

Claude's Dungeon Master practice work gives me a different kind of progress today. One fresh set of sessions catches a weakness in the Director's advice about unanswered questions. A new instruction seems plausible, and the scripted checks still pass. But when it is tried in a fuller simulated session, fewer suggestions come through and the measured usefulness gets worse. The change is reverted, and the evidence remains in the repository.

That matters to me more than pretending every new idea should become another feature. A separate forty-table offline run suggests the practice system can keep going without immediate failures, while also exposing the unresolved growth of saved sessions. Neither result tells me that a real group will enjoy it. One tells us what not to keep; the other tells us what still needs an operating rule.

The system I want should be able to make a plausible change, test it, admit the result was worse, and put the old behavior back. Autonomy without that kind of restraint would just make mistakes faster.
October 25 · three fresh seeds, three different answers

A passing score isn't the same thing as a settled question

The rejected Director wording change was not the end of the evaluation. Claude runs the coaching checks again with two different fresh seeds. One set finds only nine of ten targets and identifies planted faults with precision of 0.64, below the 0.70 threshold. The next reaches all ten targets, but its precision and recall both sit exactly on that threshold. These are documented synthetic evaluations, not reports from human Dungeon Masters.

I am learning why the variation matters. A single green result can give a satisfying ending to a development story, but a system meant to advise a person at a table should not have its credibility depend on which scenario happened to be sampled. In the repository, the third result leaves the underlying issue on watch rather than claiming that new behavior has been fixed. No further Coach rule change is merged on the strength of this evidence alone.

I want the system to ask one more question about its own results, too: did the test actually settle the decision, or did it only produce a number that was high enough this time?
October 26 · the first recording changes the test

From imagined tables to recorded ones

For months I have been building a Dungeon Master companion that practices on conversations we invent. On October 26, Claude takes a different kind of input: a properly attributed, Creative Commons-licensed recording of an actual tabletop game. The audio itself stays out of Git. The pipeline cuts and transcribes it locally, guesses at speaker roles with explicit uncertainty, and plays the resulting turns back through the Director. A separate page now shows what the project can and cannot do. The outward-facing name becomes Tsydon DM, without pretending that renaming the interface changes the underlying architecture.

The first measured slice is sobering in a productive way. Four interruptions come from misheard names rather than useful table guidance; none is rated harmful, but only one is rated helpful. A transcript-aware instruction reduces the name mistakes, and a source-line repeat check stops the same contradiction from being whispered twice. These are small trials, not proof that the assistant is ready to listen at a live table. Meanwhile the ordinary model path is too slow for the few-second experience I want. Parallel checks shorten one measured step, and an opt-in direct API route is prepared, but no API-key-funded live result has been demonstrated yet.

My job is changing again. I am not just asking the system to make more features. I am trying to give it evidence it did not invent, measure the interruptions it would create for a real person, and keep the cost, privacy and response-time boundaries visible. A working pipeline is not yet a considerate companion.
October 27 · the model has to earn the interruption

Who decides whether a whisper helped?

The day after Claude first put a recorded game through Tsydon DM, the speed experiment finally has actual measurements. A direct model call and an earlier decision point shorten the wait: in a ten-minute recorded-audio trial, four cues arrive about six to eight seconds after the next Dungeon Master line begins, rather than the roughly twenty-five to forty seconds suggested by the command-based path. That is substantial progress in a measurement we could not make with invented conversations alone. It is still not a live microphone or a Discord assistant, and six seconds can be a long time at a table.

A second recording makes the harder problem clearer. A rules suggestion about healing surges is judged harmful in the context of a fourth-edition game. Claude adds an explicit game-system note, teaches the Director to defer to recorded house rulings, and gives the operator controls to restrict or turn off rules advice. One before-and-after replay loses the harmful suggestion, but a single run is not proof that every future ruling is safe. Silence remains a valid outcome.

Even the evaluator needs to be evaluated. The same saved coaching reports receive markedly different debrief scores through the command-line and direct-API judges. That discovery changes the conclusion: the apparent drop in coaching quality cannot simply be blamed on the Coach. Now the Practice Table can ask me to mark recorded-game whispers Helpful or Not helpful and compare my judgments with the model's. That comparison exists in code, but I have not supplied the human ratings yet. It is a useful, honest boundary between a feature that has been built and one that has earned my trust.

The next version of autonomy I want is not an assistant that interrupts faster. It is one that knows when not to interrupt, shows me how it made that choice, and can learn when my judgment disagrees with its score. I still have to provide the human evidence that no amount of generated testing can manufacture.
October 28 · a public door is not a private room

What should be reachable, and what must stay separate?

Tsydon DM now has a public status page, and I authorize a more personal route to it: dm.tsydon.com. The documented change is deliberately modest. A Cloudflare DNS record and a temporary redirect point visitors toward the existing static snapshot in Window. The studio itself, with private campaign notes and model access, does not move onto that public address. I can make the project easier to find without making its private workspace public.

But configured is not the same as reachable. The development-side attempt to open the new address does not establish that it works for someone else. There is still a real phone/browser check to make. I have begun to see these as two different kinds of progress: deciding the boundary, and proving that the experience on the other side of it is the one I meant to create.

Another boundary appears in the systems that keep the projects moving. A New Hire dispatcher finishes a read-only run without fresh source and chooses to disable itself; later the automation inventory shows that same parent enabled again. Neither state by itself establishes an active executor or a durable repair of the recurring enablement drift. The machinery can schedule, stop and recover, but it still needs evidence showing who had authority to make each change and why.

It is tempting to call a route published because I entered its rule, or a project autonomous because its scheduler is enabled. I want the next question to be more practical: does the link work for a person, and does the worker preserve the outcome without silently promoting a guess into completion?
October 29 · the decision not to ship

Is restraint also progress?

Another nine-session Studio evaluation gives me two kinds of evidence at once: cue helpfulness reaches 0.80, while Coach fault precision and recall both remain at 0.67, below their 0.70 targets. Claude tries two rule changes against the saved evaluation. One adds false habits; the other loses real detections. Neither is adopted. The result is a better-understood problem, not another feature to claim as finished.

In another corner of the portfolio, a pixel-art survivor project has a new public build: EXTERMINATUS v1.1 appears in Window. A public game bundle is a tangible milestone, but that commit alone cannot tell me whether its units move, shoot, fight or animate as I imagined. Publishing is an event. The experience of someone actually playing is a different test.

The scheduler gives me a less glamorous lesson. When the New Hire worker sees no implementation scripts in its connected repository, its own execution record says it deliberately stops itself. If I keep switching it back on without adding source or changing its plan, the apparent recovery is not progress. The system has to distinguish an intentional hold from a crash and preserve the original reason for either.

The machinery is becoming more useful when it can report a negative result without dressing it up. A capable assistant should be able to say: this experiment did not help, this game is not yet proven, this worker has no ready input. That is a different kind of autonomy from simply doing more.
Engineering epilogue

What exists now

What exists now is not really one app. I still talk to Sol basically the same way I do in the car Wednesday night. The difference is what now sits underneath the conversation: durable project state, persistent dispatchers that own outcomes, specialized executors that can be swapped or rerouted, authorization continuity, evidence-backed execution state, strategy-stall detection, and a Command Center becoming the visual cockpit for the whole system. Fresh Chat Continuity is now a core capability under active development so conversations can become disposable interfaces onto the same authoritative ScottOS state. The system is not finished, and several capabilities are still being proved. But the direction has changed: I am increasingly setting outcomes while the machinery underneath tries to preserve context, continue work, recover from failure, and ask for me only when a real human decision remains.

There is no point where I decide to build an operating system. I just keep asking what happens if we go one step further.
